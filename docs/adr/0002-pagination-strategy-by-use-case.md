# ADR-0002 : 게시글 목록 조회에서 조회 목적별 페이지네이션 전략을 분리한 이유

## Date
2026.04.24 (금)

## Context
초기에는 전체 게시글 조회에 Keyset pagination을 적용했다.
하지만 당시 결정은 사용자의 조회 방식이나 게시판별 UX를 고려했다기보다는, Offset보다 Keyset이 빠르다는 이유에 가까웠다.

이후 게시글 목록 조회를 사용자 흐름 기준으로 다시 검토했다.

게시글 전체 조회는 사용자가 게시판을 둘러보는 흐름이다.
따라서 페이지 번호 이동, 전체 개수 확인, 특정 페이지 접근이 가능한 Offset + Page 방식이 게시판 UX에 적합하다고 판단했다.

반면 검색 조회는 사용자가 특정 키워드에 맞는 결과를 빠르게 찾는 흐름이다.
검색 결과에서는 전체 페이지 수보다 상위 결과의 관련성과 다음 결과 존재 여부가 더 중요하다.
사용자가 검색 결과의 깊은 페이지까지 숫자 버튼을 눌러가며 탐색할 가능성은 낮다고 판단했다.

따라서 게시글 전체 조회와 검색 조회의 페이지네이션 전략을 분리한다.

댓글은 전체 페이지 수보다 다음 댓글 존재 여부가 중요하므로 Slice를 사용한다.

최신글 더보기나 무한스크롤 API가 필요해지면 Keyset 방식을 별도 API로 제공한다.

---

## Decision
조회 대상과 사용 흐름에 따라 Page, Slice, Keyset을 분리해서 사용한다.

- 게시글 전체 조회: Offset + Page
- 게시글 검색 조회: Offset + Slice
- 댓글 조회: Offset + Slice

게시글 전체 조회는 게시판 탐색 목적이므로 전체 개수와 전체 페이지 수를 제공한다.

게시글 검색 조회는 특정 결과를 찾는 목적이므로 전체 개수 계산보다 다음 검색 결과 존재 여부를 우선한다.
따라서 검색 조회에서는 count query 비용을 줄이기 위해 Slice 방식을 사용한다.

---

## Options Considered

### 1. 기존 Keyset pagination 유지
- 장점: 깊은 페이지 조회에서도 성능이 안정적이다.
- 단점: 페이지 번호 이동이 어려워 일반 게시판 목록 UX에 맞지 않는다.

### 2. 게시글 전체 조회와 검색 조회 모두 Offset + Page 사용
- 장점: 전체 개수, 전체 페이지 수, 숫자 기반 페이지 이동을 제공할 수 있다.
- 단점: 검색 결과가 많을 경우 count query 비용이 커질 수 있다.
- 판단: 전체 조회에는 적합하지만, 검색 조회에는 과한 정보를 제공한다고 판단했다.

### 3. 게시글 전체 조회는 Page, 검색 조회는 Slice로 분리 (선택)
- 장점: 전체 조회는 게시판 탐색 UX를 유지하고, 검색 조회는 count query 비용을 줄일 수 있다.
- 단점: 조회 목적에 따라 응답 형식이 달라지므로 API 설계와 프론트 처리 방식이 나뉜다.
- 판단: 조회 목적이 다르므로 동일한 페이지네이션 전략을 강제하는 것보다 분리하는 것이 적절하다고 판단했다.

### 4. 검색 전용 엔진 도입
- 장점: 대량 검색, 정렬, 랭킹, 형태소 분석에 유리하다.
- 단점: 별도 인프라와 데이터 동기화 비용이 발생한다.
- 판단: 현재 단계에서는 MySQL 기반 검색 최적화를 우선하고, 검색 요구사항이 커질 경우 별도 검토한다.

---

## Consequences

### 좋은 점
- 게시글 전체 조회는 기존 게시판처럼 숫자 기반 페이지 이동을 제공할 수 있다.
- 검색 조회는 전체 개수 계산을 생략하여 count query 비용을 줄일 수 있다.
- 댓글 조회도 기존처럼 더보기 흐름에 맞게 처리할 수 있다.
- 조회 목적별로 Page와 Slice를 구분한 근거를 명확히 설명할 수 있다.

### 나쁜 점 / 트레이드오프
- 검색 결과에서는 totalElements와 totalPages를 제공하지 않는다.
- 검색 결과 UI는 숫자 페이지 버튼보다 이전/다음 또는 더보기 방식에 더 적합해진다.
- 조회 방식이 나뉘므로 응답 객체와 테스트 케이스가 증가한다.
- 전체 조회와 검색 조회의 API 응답 정책을 프론트와 명확히 맞춰야 한다.
