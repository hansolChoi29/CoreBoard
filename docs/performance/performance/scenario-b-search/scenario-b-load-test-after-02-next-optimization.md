# Load Test After 02 - 검색 정렬 비용 추가 분석

## 1. 분석 목적

Scenario B 1차 개선 후에도 검색 목록 조회 API는 p95 3초 기준을 통과하지 못했다.

1차 개선으로 count query와 users 추가 조회는 제거되었지만, 검색 목록 조회 API의 p95는 9678ms로 측정되었다.

따라서 남은 병목이 FULLTEXT 검색 자체인지, 검색 결과 정렬 비용인지 확인한다.

---

## 2. 비교 대상

| 항목     | 내용                                              |
|--------|-------------------------------------------------|
| 대상 API | `GET /posts/search?keyword=test&page=0&size=10` |
| 데이터 조건 | 게시글 약 142만 건                                    |
| 비교 기준  | `ORDER BY` 포함 여부                                |
| 확인 항목  | 실행 시간, `Using filesort` 발생 여부                   |

---

## 3. 추가 분석 결과

| 쿼리 조건                                  | 단일 요청 시간 | 실행 계획                | 해석               |
|----------------------------------------|---------:|----------------------|------------------|
| `ORDER BY created_at DESC` 포함          |     약 8초 | `Using filesort` 발생  | 검색 결과 정렬 비용 큼    |
| `ORDER BY` 제거                          |  약 0.33초 | `Using filesort` 사라짐 | 정렬 제거 시 응답 시간 급감 |
| `ORDER BY score DESC, created_at DESC` |     약 8초 | 정렬 비용 지속             | 관련도 정렬도 병목 해소 못함 |

---

## 4. 결과 해석

`ORDER BY created_at DESC`를 제거하자 단일 요청 시간이 약 8초에서 0.33초로 감소했다.

실행 계획에서도 `Using filesort`가 사라졌다.

따라서 현재 검색 지연에는 FULLTEXT 검색 결과 후보를 정렬하는 비용이 크게 포함되어 있다고 판단한다.

다만 `ORDER BY`를 제거하면 검색 결과의 노출 순서를 설명하기 어렵다.

사용자 입장에서도 검색 결과가 매번 안정적인 순서로 제공되지 않을 수 있다.

따라서 정렬 제거는 최종 적용하지 않는다.

---

## 5. 결론

Scenario B는 MySQL FULLTEXT 기반 1차 개선으로 응답 시간은 줄었지만, 목표 기준인 p95 3초에는 도달하지 못했다.

추가 분석 결과, 남은 병목은 특정 정렬 컬럼 하나의 문제가 아니라 FULLTEXT 검색 결과 후보를 정렬하는 작업 자체로 판단한다.

따라서 이번 단계에서는 MySQL 기반 검색 최적화의 한계를 확인한 것으로 정리한다.

Elasticsearch 도입은 후속 개선 과제로 분리한다.
