# Load Test

## 1. 테스트 목적

Scenario B - 검색 사용자의 흐름에서 1차 개선 이후 응답 시간이 얼마나 개선되었는지 확인한다.

이번 테스트는 기존 검색 조회 병목을 줄이기 위해 다음 변경을 적용한 뒤 수행했다.

- 검색 API를 `/posts/search`로 분리
- 검색 조회를 Page에서 Slice로 전환
- count query 제거
- Post 엔티티 조회 대신 Projection 기반 조회 적용
- 작성자 닉네임 조회를 위한 users 추가 조회 제거
- MySQL FULLTEXT 검색 적용

이번 테스트의 목적은 개선 후에도 검색 목록 조회 API가 목표 기준인 p95 3초 이내에 들어오는지 확인하고, 기준을 초과할 경우 남은 병목 구간을 다시 좁히는 것이다.

## 9. 결과 해석

1차 개선 이후 검색 API는 기존 게시판별 검색 구조에서 전체 게시글 검색 구조로 변경되었다.

검색 조회는 Page에서 Slice로 전환하여 count query를 제거했고, Post 엔티티 조회 대신 Projection 기반 조회를 사용하여 작성자 닉네임 조회 과정에서 발생하던 users 추가 조회도
제거했다.

그 결과 검색 API 실행 SQL은 검색 목록 조회 SQL 1개로 줄었다.

개선 전 5 users 테스트에서는 검색 목록 조회 API의 평균 응답 시간이 약 19407ms, p95가 약 20367ms였다.

1차 개선 후 5 users 테스트에서는 검색 목록 조회 API의 평균 응답 시간이 6805ms, p95가 9678ms로 감소했다.

따라서 Projection 적용과 Slice 전환은 응답 시간 개선에 효과가 있었다.

하지만 목표 기준인 p95 3초에는 여전히 도달하지 못했다.

Grafana 지표상 CPU 사용률이 높은 수준으로 지속되지 않았고, DB Connection Pending도 발생하지 않았다.

따라서 현재 병목은 서버 CPU 포화나 DB Connection Pool 부족보다는, `MATCH ... AGAINST ... ORDER BY created_at DESC LIMIT ?` 검색 SQL 자체의 실행
비용으로 좁혀진다.

## 10. 결론

Scenario B - 검색 사용자의 흐름에 대해 1차 개선 후 5 users Load Test를 수행했다.

개선 결과, 검색 목록 조회 API의 평균 응답 시간은 기존 약 19407ms에서 6805ms로 감소했고, p95는 기존 약 20367ms에서 9678ms로 감소했다.

오류율은 0.00%로 유지되었고, 검색 결과 상세 조회 API는 p95 12ms로 정상 범위에 있었다.

그러나 검색 목록 조회 API의 p95가 9678ms로 측정되어 목표 기준인 3초를 초과했다.

따라서 10/20/30 users 단계는 진행하지 않고 테스트를 중단했다.

이번 테스트를 통해 count query와 users 추가 조회는 제거되었지만, 전체 게시글 검색 SQL 자체의 실행 비용이 여전히 주요 병목으로 남아 있음을 확인했다.
