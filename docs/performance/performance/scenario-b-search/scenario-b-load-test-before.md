# Load Test

## 1. 테스트 목적

CoreBoard의 검색 사용자 흐름에서 대량 데이터 기준 API 응답 시간이 안정적으로 유지되는지 확인한다.

이번 테스트는 단일 API만 호출하는 방식이 아니라, 사용자가 실제로 검색 결과를 조회한 뒤 게시글 상세 화면으로 이동하는 흐름을 기준으로 구성했다.

특히 약 142만 건의 게시글 데이터가 존재하는 상황에서 검색 목록 조회 API가 목표 응답 시간 안에 처리되는지 확인하고, 중단 기준을 초과하는 경우 병목 분석 대상으로 분리한다.

## 9. 결과 해석

Scenario B 테스트에서는 5 users 단계부터 검색 목록 조회 API의 응답 시간이 중단 기준을 초과했다.

검색 목록 조회 API는 평균 19407ms, p95 20367ms로 측정되었다. 반면 검색 결과 게시글 상세 조회 API는 평균 10ms, p95 12ms로 안정적으로 응답했다.

따라서 응답 지연은 전체 API에 고르게 발생한 것이 아니라, 검색 조건이 포함된 게시글 목록 조회 API에 집중된 것으로 판단한다.

Grafana 지표상 CPU 사용률이 높은 수준으로 지속되지 않았고, JVM Heap Memory의 급격한 증가나 OOM 징후도 확인되지 않았다. 또한 DB Connection Pending이 발생하지 않았기 때문에
DB Connection Pool 부족으로 요청이 대기한 상황은 아닌 것으로 보인다.

즉, 현재 단계에서는 서버 전체 자원 부족보다는 검색 목록 조회 요청 내부의 처리 비용을 우선 의심한다.

이후 Bottleneck Analysis 문서에서 실제 실행 SQL, count query 실행 여부, EXPLAIN 결과, 인덱스 사용 여부, 정렬 비용을 기준으로 원인을 추가 분석한다.

## 10. 결론

Scenario B - 검색 사용자의 흐름 Load Test 결과, 5 users 단계에서 검색 목록 조회 API의 p95 응답 시간이 20367ms로 측정되어 중단 기준인 3초를 크게 초과했다.

상세 조회 API는 p95 12ms로 안정적으로 응답했기 때문에, 병목은 게시글 상세 조회가 아니라 검색 조건이 포함된 게시글 목록 조회 API에 집중된 것으로 판단한다.

CPU, JVM Memory, DB Connection 지표에서는 명확한 자원 포화 징후가 확인되지 않았다. 따라서 이번 테스트 결과는 서버 장애나 전체 자원 부족보다는 검색 목록 조회 API 내부의 쿼리 실행
비용을 의심하게 만드는 결과로 정리한다.

후속 문서인 Bottleneck Analysis에서는 검색 목록 조회 API의 실제 SQL과 실행 계획을 확인하여 병목 원인을 좁힌다.
