# Load Test

## 1. 테스트 목적

Scenario B - 검색 사용자의 흐름에서 대량 게시글 데이터가 존재하는 상태로 검색 조건이 포함된 게시글 목록 조회와 검색 결과 게시글 상세 조회의 응답 시간, p95, 오류율, 처리량 변화를 확인한다.

이번 테스트는 약 140만 건의 게시글 데이터와 약 14만 건의 `test` 검색 대상 데이터가 존재하는 상태에서 수행한다.

검색 API는 조건 필터링, 정렬, count query 비용이 발생할 수 있으므로, 대량 데이터 조건에서 검색 요청이 응답 시간에 어떤 영향을 주는지 확인한다.

또한 Prometheus와 Grafana를 통해 CPU, JVM Heap Memory, DB 연결 사용 상태를 함께 확인하여 검색 요청이 애플리케이션과 DB 자원에 미치는 영향을 관찰한다.

## 9. 결과 해석

Scenario B Load Test는 5 users 단계에서 중단 기준에 도달했다.

검색 조건이 포함된 게시글 목록 조회 API는 평균 11999ms, p95 19632ms, 최대 20301ms로 측정되었다. 이는 목표 기준인 p95 1.5초 이하를 크게 초과하며, 공통 중단 기준인 p95 3초
초과에도 해당한다.

반면 검색 결과 게시글 상세 조회 API는 평균 9ms, p95 23ms, 최대 28ms로 안정적으로 응답했다.

따라서 이번 지연은 전체 시나리오 또는 서버 전체 문제가 아니라, 검색 조건이 포함된 게시글 목록 조회 API에 집중된 병목으로 판단된다.

모니터링 결과 DB 연결 대기 요청은 발생하지 않았다. 즉, DB 연결을 얻지 못해서 요청이 밀린 상황은 아니며, 연결을 얻은 뒤 실행되는 검색 쿼리 자체가 오래 걸렸을 가능성이 높다.

현재 post 테이블에는 board_id, user_id 인덱스만 존재한다. 검색 조건은 `keyword=test`, 정렬은 `direction=DESC`로 수행되므로, 대량 데이터 조건에서는 LIKE 검색, 정렬,
count query, 인덱스 부재가 주요 병목 후보가 될 수 있다.

따라서 10 users, 20 users, 30 users 단계는 실행하지 않고 테스트를 중단했다. 이후 Bottleneck Analysis를 통해 검색 목록 조회 쿼리의 실행 계획과 인덱스 사용 여부를 확인한다.

## 10. 결론

Scenario B - 검색 사용자의 흐름은 약 140만 건의 게시글 데이터 조건에서 5 users 단계부터 성능 병목이 확인되었다.

검색 목록 조회 API의 p95 응답 시간이 19632ms로 측정되어 중단 기준을 초과했기 때문에, 추가 부하 단계인 10 users, 20 users, 30 users는 실행하지 않았다.

상세 조회 API는 안정적으로 응답했으므로, 병목 대상은 검색 조건이 포함된 게시글 목록 조회 API로 좁혀진다.

이번 결과를 바탕으로 다음 단계에서는 Bottleneck Analysis를 수행한다. 주요 확인 대상은 검색 쿼리, count query, 정렬 비용, LIKE 검색 비용, 인덱스 사용 여부다.

개선 적용 후에는 동일한 조건에서 다시 5 users부터 측정하고, 5 users 기준을 통과하면 10 users, 20 users, 30 users 순서로 부하를 증가시킨다.
