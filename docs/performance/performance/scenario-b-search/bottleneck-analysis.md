# Bottleneck Analysis

## 1. 분석 목적

Scenario B - 검색 사용자의 흐름에서 검색 목록 조회 API가 5 users 단계부터 p95 3초 기준을 초과했다.

이번 분석의 목적은 병목이 검색 결과 상세 조회, 서버 자원 부족, DB Connection 부족, JVM Memory 문제가 아니라 검색 목록 조회 쿼리 자체에 있는지 확인하는 것이다.

---

## 2. 분석 대상

| 항목     | 내용                      |
|--------|-------------------------|
| 시나리오명  | Scenario B - 검색 사용자의 흐름 |
| 테스트 환경 | local                   |
| 데이터 조건 | 게시글 약 142만 건            |
| 기준 테스트 | 5 users Load Test       |
| 분석 일자  | 2026-05-20              |

## 3. 최초 관찰 결과

| API                                                              | 평균 응답 시간 |     p95 | 해석             |
|------------------------------------------------------------------|---------:|--------:|----------------|
| `GET /posts/search?keyword=test&page=0&size=10` |  19407ms | 20367ms | 검색 목록 조회 지연 발생 |
| `GET /posts/{id}`                                                |     10ms |    12ms | 상세 조회는 정상 범위   |

검색 결과 상세 조회는 안정적이었다.

따라서 병목은 검색 결과 상세 조회가 아니라, 검색 조건이 포함된 게시글 목록 조회 API에 집중되어 있다고 판단했다.

## 4. 자원 관점 확인

| 항목            | 관찰 결과                   | 판단               |
|---------------|-------------------------|------------------|
| CPU           | 높은 수준으로 지속되지 않음         | CPU 병목 가능성 낮음    |
| JVM Memory    | OOM 징후 없음               | 메모리 병목 가능성 낮음    |
| DB Connection | Pending Connection 0 유지 | 커넥션 풀 부족 가능성 낮음  |
| 오류율           | 0.0%                    | 장애가 아니라 응답 지연 문제 |

서버 자원 부족보다는 검색 쿼리 실행 비용이 주요 원인으로 보였다.

---

## 5. 1차 개선 내용

검색 목록 조회 병목을 줄이기 위해 다음 개선을 적용했다.

| 개선 항목                       | 목적               |
|-----------------------------|------------------|
| LIKE 검색 → MySQL FULLTEXT 검색 | 검색 조건 처리 비용 감소   |
| Page → Slice                | count query 제거   |
| Post 엔티티 조회 → Projection 조회 | 필요한 컬럼만 조회       |
| writerName을 JOIN으로 조회       | users 추가 조회 제거   |
| `/posts/search` API 분리      | 전체 게시글 검색 흐름 명확화 |

개선 후 검색 API는 목록 조회 SQL 1개만 실행되었다.

---

## 6. 1차 개선 후 결과

| 항목             |    개선 전 | 1차 개선 후 |
|----------------|--------:|--------:|
| 검색 목록 평균 응답 시간 | 19407ms |  6805ms |
| 검색 목록 p95      | 20367ms |  9678ms |
| 오류율            |    0.0% |    0.0% |

1차 개선으로 응답 시간은 크게 감소했다.

하지만 5 users 기준 p95가 9678ms로 측정되어 목표 기준인 3초에는 도달하지 못했다.

---

## 7. 추가 분석 결과

EXPLAIN 결과, FULLTEXT 인덱스는 사용되고 있었다.

그러나 정렬 조건이 포함되면 `Using filesort`가 발생했다.

정렬 비용을 확인하기 위해 단일 요청 시간을 비교했다.

| 쿼리 조건                                  | 단일 요청 시간 | 해석               |
|----------------------------------------|---------:|------------------|
| `ORDER BY created_at DESC`             |     약 8초 | 최신순 정렬 비용 큼      |
| `ORDER BY` 제거                          |  약 0.33초 | 정렬 제거 시 응답 시간 급감 |
| `ORDER BY score DESC, created_at DESC` |     약 8초 | 관련도 정렬도 개선 효과 없음 |

따라서 남은 병목은 FULLTEXT 검색 자체보다, 대량 검색 결과를 정렬하는 비용으로 판단했다.

---

## 8. 최종 판단

정렬을 제거하면 응답 시간은 크게 줄어든다.

하지만 정렬 없는 검색은 결과 순서를 설명하기 어렵고, 사용자에게 안정적인 검색 결과를 제공하기 어렵다.

따라서 정렬 제거는 최종 적용하지 않는다.

MySQL FULLTEXT 기반 개선은 1차 개선 단계에서 종료한다.

Elasticsearch 도입은 전체 부하 테스트 완료 후 별도 개선 과제로 검토한다.

---

## 9. 결론

Scenario B의 병목은 검색 결과 상세 조회가 아니라 검색 목록 조회 API에 있었다.

1차 개선으로 count query와 users 추가 조회는 제거했고, 검색 목록 조회 p95는 20367ms에서 9678ms로 감소했다.

그러나 목표 기준인 p95 3초에는 도달하지 못했다.

추가 분석 결과, 남은 병목은 대량 FULLTEXT 검색 결과를 정렬하는 비용이었다.

따라서 Scenario B는 MySQL FULLTEXT 기반 1차 개선과 한계 확인 단계에서 종료한다.

추가로 `ORDER BY` 제거 여부를 비교한 결과, 정렬 제거 시 단일 요청 시간이 약 8초에서 0.33초로 감소했다.

따라서 남은 병목은 FULLTEXT 검색 자체만의 문제가 아니라, 검색 결과 후보를 정렬하는 비용으로 판단한다.

다만 정렬 없는 검색 결과는 사용자에게 일관된 순서를 제공하기 어렵기 때문에 최종 적용하지 않는다.
