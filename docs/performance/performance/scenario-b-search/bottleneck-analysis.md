# Bottleneck Analysis

## 1. 분석 목적

Scenario B - 검색 사용자의 흐름 Load Test에서 5 users 단계부터 검색 목록 조회 API의 응답 시간이 중단 기준을 초과했다.

이번 분석의 목적은 검색 흐름 중 어떤 API에서 병목이 발생했는지 확인하고, 해당 병목이 DB Connection 부족, JVM Memory 문제, 서버 자원 부족 때문인지 또는 검색 쿼리 자체의 실행 비용
때문인지 원인을 좁히는 것이다.

## 7. 추가 확인 내용

### 7.1 쿼리 확인

검색 목록 조회 조건은 다음과 같다.

```sql
SELECT *
FROM post
WHERE board_id = 2
  AND status = 'PUBLISHED'
  AND (title LIKE '%test%' OR content LIKE '%test%')
ORDER BY created_at DESC LIMIT 10;
```

count query는 다음과 같은 형태로 확인했다.

```sql
SELECT COUNT(*)
FROM post
WHERE board_id = 2
  AND status = 'PUBLISHED'
  AND (title LIKE '%test%' OR content LIKE '%test%');
```

### 7.2 인덱스 확인

현재 `post` 테이블에는 다음 인덱스가 존재한다.

| 인덱스                         | 컬럼       |
|-----------------------------|----------|
| PRIMARY                     | id       |
| FK2t7katxxymxif93a9osshl0ns | board_id |
| FK7ky67sgi7k0ayf22652f7763r | user_id  |

검색 목록 조회 EXPLAIN 결과는 다음과 같다.

| 항목       | 결과                          |
|----------|-----------------------------|
| type     | ref                         |
| key      | FK2t7katxxymxif93a9osshl0ns |
| rows     | 702250                      |
| filtered | 10.49                       |
| Extra    | Using where; Using filesort |

count query EXPLAIN 결과는 다음과 같다.

| 항목       | 결과                          |
|----------|-----------------------------|
| type     | ref                         |
| key      | FK2t7katxxymxif93a9osshl0ns |
| rows     | 702250                      |
| filtered | 10.49                       |
| Extra    | Using where                 |

해석하면, MySQL은 `board_id` 인덱스만 사용한 뒤 약 70만 건을 대상으로 `status`, `title LIKE`, `content LIKE` 조건을 검사하고 있다.

또한 검색 목록 조회에서는 `ORDER BY created_at DESC` 정렬을 인덱스로 해결하지 못해 `Using filesort`가 발생했다.

이번 테스트에서는 5xx 오류나 애플리케이션 예외가 발생하지 않았다.

### 7.4 Grafana 지표 확인

해당 없음.

CPU, JVM Memory, DB 연결 대기 지표에서 병목으로 판단할 만한 이상 징후는 확인되지 않았다.

## 10. 결론

Scenario B Load Test에서 발생한 병목은 검색 결과 상세 조회가 아니라, 검색 조건이 포함된 게시글 목록 조회 API에 집중되어 있었다.

검색 목록 조회 API는 5 users 조건에서 평균 10216ms, p95 12085ms로 측정되어 중단 기준을 초과했다. 반면 검색 결과 게시글 상세 조회 API는 p95 9ms로 안정적으로 응답했다.

EXPLAIN 결과, 검색 목록 조회 쿼리는 `board_id` 인덱스만 사용하고 있었으며 약 702250건을 대상으로 조건 검사를 수행했다. 또한 `ORDER BY created_at DESC` 정렬 과정에서
`Using filesort`가 발생했다.

따라서 이번 병목의 주요 원인은 DB Connection 부족이나 JVM Memory 문제가 아니라, 대량 데이터 조건에서 검색 목록 조회 쿼리의 필터링 범위가 크고 정렬 비용이 발생했기 때문으로 판단한다.

다음 단계에서는 `(board_id, status, created_at)` 복합 인덱스를 추가하여 검색 목록 조회의 정렬 비용을 줄일 수 있는지 확인하고, 개선 전후 JMeter 결과와 EXPLAIN 결과를
비교한다.
